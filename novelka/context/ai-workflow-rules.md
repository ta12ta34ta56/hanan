# AI Workflow Rules — Novelka

> Direct instructions to the coding agent. These are RULES, not suggestions. Follow them
> on every unit.

---

## Overall approach

- **Spec-driven and incremental.** Work from `context/specs/*.md`. Implement one unit at
  a time. Do exactly what the spec says — no more, no less.
- **Think before you build.** When a spec is ambiguous, read `project-overview.md`,
  `architecture.md`, and `ui-context.md`. If it is STILL ambiguous, ask — do not guess.

---

## Scoping rules

1. **One unit at a time.** Do not combine unrelated changes in one unit.
2. **No speculative changes.** Do not refactor, rename, or "improve" code outside the
   unit's scope even if it looks messy. If something is broken and in your way, note it
   in the progress tracker and mention it; do not silently rewrite it.
3. **Stay inside one system boundary per unit** — don't mix UI changes with engine
   changes with storage changes in one unit unless the spec explicitly says so.
4. **Introduce dependencies just in time.** Only add a package in the unit where it
   first unlocks real behavior.

---

## Split work when

- A unit is touching more than one system boundary.
- You cannot verify a meaningful checkpoint mid-way.
- The spec is large enough that a single session would drift. Split into smaller spec
  files rather than guessing.

---

## Missing or ambiguous requirements

- If a requirement is **undefined**, do NOT invent it. Ask a clarifying question with
  two or three concrete options.
- If a requirement **contradicts an invariant** in `architecture.md`, stop and flag it —
  do not silently violate the invariant.
- If a value could go several ways (colors, wording, layout), prefer the existing
  convention in `ui-context.md` and `code-standards.md`; otherwise ask.

---

## Files you must not modify without explicit instruction

- `src/services/kdp-cover.ts` — the cover/spine math is correct and must not be rewritten.
- `src/services/kdp.ts` — the KDP margin/safe-area math (reuse it).
- Generator **algorithms** (`*/generator.ts`) — the puzzle generation logic is reused,
  not rewritten.
- The design-token definitions in `src/index.css` (you may add tokens if a new semantic
  need appears, but do not silently repaint existing tokens).
- Any `.built.mjs` artifacts (generated by the test scripts).

---

## Keep documentation in sync

- After any change that affects scope, architecture, standards, or UI, update the
  relevant `context/*.md` file BEFORE continuing.
- Update `context/progress-tracker.md` after every meaningful implementation change.

---

## Verification checklist (before a unit is done)

- [ ] Matches the spec exactly — no extra features.
- [ ] No TypeScript errors (`tsc -b`).
- [ ] No lint errors (`npm run lint`).
- [ ] Relevant unit tests pass.
- [ ] `npm run build` passes.
- [ ] No console errors in the dev server.
- [ ] Works in both light and dark themes (where UI is involved).
- [ ] Respects all invariants in `architecture.md`.
- [ ] Updated `context/progress-tracker.md`.

---

## When the agent gets stuck or output drifts

- **Do not paper over bugs with more code.** Identify the root cause.
- If the change you made breaks something, revert the smallest set needed and report the
  cause, rather than layering fixes.
- If instructions conflict, the order of authority is:
  1. `context/specs/*.md` (the specific unit)
  2. `context/architecture.md` (invariants)
  3. `context/project-overview.md` (scope)
  4. `context/ui-context.md` and `context/code-standards.md` (conventions)
  5. `context/ai-workflow-rules.md` (process)
